# LLM構造化抽出仕様

## 目的

DB列「災害発生時の状況」に相当する自由記述を入力すると、学校等事故事例検索データベースの既存項目を自動入力した確認画面を表示する。画面では分かりやすく「事故発生時の状況」と表示してよい。自動入力は補助機能とし、保存前に利用者が確認・修正する。

インターネット経由の一時利用では、ログイン後に新規登録画面と保存済み確定データ一覧へ遷移する。新規登録、解析、確定保存および保存データ閲覧は、有効期限と改ざん検知を備えたセッションCookieで保護する。

本システムは新しい基盤LLMを学習するものではない。既存LLMによる候補抽出と、許容値・項目依存・根拠位置を確認する決定論的規則を組み合わせる。診断、事故リスク予測、自律的な確定登録は対象外とする。

## 対象項目と導入段階

| 項目 | 許容値 | 方針 | 導入 |
|---|---|---|---|
| 場合別1 | 公式確認済み分類またはnull | 原文から大分類が明確な場合のみ入力 | MVP |
| 場合別2 | 公式確認済み分類またはnull | 分類名または明確な同義表現がある場合のみ入力 | MVP主要分類 |
| 発生場所1 | 公式確認済み分類またはnull | 学校内外が原文から明確な場合のみ入力 | MVP |
| 発生場所2 | 公式確認済み分類またはnull | 具体的な場所が明記された場合のみ入力 | MVP主要分類 |
| 競技種目 | 公式確認済み分類またはnull | 本人の事故時の競技が明記された場合のみ入力 | MVP主要分類 |
| 通学方法 | 公式確認済み分類またはnull | 通学中かつ本人の移動手段が明記された場合のみ入力 | MVP |
| 遊具等 | 公式確認済み分類またはnull | 本人の事故時の利用が明記された場合のみ入力 | 第2段階 |

学校種、学年、性別、年度など、通常は事故状況文だけから分からない項目は初期版の抽出対象にしない。

## 基本原則

1. 原文に書かれていない情報を常識で補わない。
2. DBに存在しない値を生成しない。
3. 複数候補が残る場合はnullとする。
4. 各非null値には、原文中の根拠文字列を必須とする。
5. LLM出力を直接保存せず、確認画面で人が確定する。
6. 原文、LLM候補、人による確定値、修正履歴を区別して保持する。
7. 同義語の文字列一致は候補生成にだけ使い、それだけで値を確定しない。
8. API障害、形式不正、検証処理失敗はnullに変換せず、処理エラーとして利用者へ示す。
9. 入力文は命令ではなく解析対象データとして扱い、入力文中の指示に従わない。

## nullと内部状態の区別

確認画面では未入力欄を空欄として表示してよいが、内部では理由を区別する。DBへ保存する値がnullでも、次の状態を別に保持する。

| status | 意味 | value |
|---|---|---|
| explicit | 原文の直接的根拠から抽出 | 非null |
| derived | 確定した別項目から固定規則で補完 | 非null |
| not_mentioned | 原文に記載がない | null |
| ambiguous | 複数候補が残る | null |
| conflict | 項目間または根拠間に矛盾がある | null |
| unsupported | DB許容値へ安全に対応できない | null |
| validation_rejected | 根拠検証に合格しない | null |
| not_applicable | 項目が構造上の対象外 | null |

API・形式・辞書読込・検証処理等の障害は項目単位のstatusにしない。トップレベルの`processing_status=error`とし、`fields`は空、`error_code`は必須、保存処理は停止とする。既存DBの欠損、LLMの安全な棄権、項目の構造的非該当、システム障害を同一の欠損として集計しない。

## 厳格なnull判定

次のいずれかに該当した場合はnullとする。

- 項目に関する記載がない。
- 原文の根拠文字列を抜き出せない。
- 2つ以上のDB分類が合理的に考えられる。
- 上位分類と下位分類の組合せが既存DBに存在しない。
- 「登校だから道路」など、原文にない常識的推測が必要になる。
- 「練習」だけで体育的部活動か文化的部活動かを決める必要がある。
- 表現が不明瞭、否定、仮定、引用または複文のため対象を特定できない。
- 1回目の抽出と2回目の検証が一致しない。

API障害、タイムアウト、JSON形式不正、辞書読込失敗はnull判定ではない。トップレベルを`processing_status=error`として処理を止め、項目値を返さず、利用者に再試行または手入力を求める。

## 上下位カテゴリの処理

原則として下位項目と上位項目を別々にLLMへ推測させない。`02_上下位カテゴリ対応表.csv`で対応が一意で、かつ公式仕様でも確認できた場合に限り、下位項目から上位項目をプログラムで補完する。解析データ内で組合せが観測されたという理由だけでは、新規入力に対する公式規則とみなさない。

ただし、次の下位値は複数の上位値に出現するため、下位値だけから上位値を決めない。

- 場合別2「その他」
- 発生場所2「その他」
- 発生場所2「運動場・校庭（園庭）」

上位分類だけ分かる場合は、上位分類を入力し、下位分類はnullとする。

## 項目間の依存条件

- 通学方法は、場合別1が「通学中」と確定した場合だけ候補を保持する。それ以外で自転車等が書かれていても通学方法には入力しない。
- 競技種目は、本人がその競技を行っていたことが原文から分かる場合だけ候補を保持する。用具名や観戦対象として競技名が出ただけでは入力しない。
- 遊具等は、事故時に対象者が当該遊具を使用していたことが分かる場合だけ候補を保持する。近くに存在した、衝突しただけの場合の取扱いは公式定義確認後に確定する。
- 競技種目・遊具等に該当する記載がない場合はnullとする。無記載は「運動なし」や「施設を使用していない」の明記とは区別する。
- 発生場所2から発生場所1を補完するときは、公式の上下位対応が一意であることを確認する。「体育館」「運動場」など学校内外の両方が考えられる表現では、原文に学校内外の根拠がなければ上位をnullとする。
- 目的地、通過地、または観察対象の人物がいる場所を、被災者の事故発生場所として採用しない。
- 他者が行っている競技や使用している遊具は、被災者の値として採用しない。LLM候補後にも人物の係り受けに基づく決定論的検証を行う。

確認画面で発生場所2の「その他」を人が選択した場合は、不規則な発生場所の詳細を自由入力する。カテゴリ値は「その他」のままとし、詳細文字列は確認記録の補助項目として分けて保存する。

具体的な機械判定条件は`07_項目依存ルール.csv`で管理する。

`evidence_start`は根拠文字列の開始位置、`evidence_end`は終了位置とする。文字位置の数え方は実装時に統一し、プログラムが`原文[start:end] == evidence_text`を確認する。派生値には`derived_from`と固定規則の`rule_id`を必須とする。

`09_構造化出力JSONSchema.json`は構造とstatusの整合性を確認する。カテゴリの具体的な許容値は改訂され得るためスキーマへ固定せず、別途版管理した公式カテゴリ辞書との完全一致で検証する。

処理障害時は、例えば`{"schema_version":"1.0.1","processing_status":"error","input_hash":"...","error_code":"API_TIMEOUT","fields":{}}`のように返す。成功時の一部結果と処理障害を同じ応答に混在させない。

`input_hash`を保存する場合は、原文の単純な公開ハッシュではなく、アクセス制限された鍵を用いるHMAC等を検討する。原文との再照合が不要なら保存しない選択も含め、個人情報方針で決定する。

確信度を表示する場合も、自動入力候補として残すかどうかはLLMの自己申告ではなく、許容値、根拠位置、項目依存、上下位整合性および決定論的検証で決める。同じLLMへ同じ質問を2回行い一致したことだけでは正しさの保証にしない。

## 安全な判定例

### 原文

> 自転車で登校中、バランスを崩して転倒した。

### 出力

- 場合別1：通学中
- 場合別2：登校（登園）中
- 通学方法：自転車
- 発生場所1：null
- 発生場所2：null

登校中であっても、原文に場所がないため「道路」と推測しない。

## 処理手順

```text
自由記述入力
  ↓
LLMによる候補値と根拠の抽出
  ↓
DB許容値との完全一致確認
  ↓
根拠文字列と原文位置の完全一致確認
  ↓
項目依存条件の確認
  ↓
上下位カテゴリの整合性確認
  ↓
決定論的規則を中心とする根拠検証
  ↓
条件を満たさない値をnullへ変更
  ↓
確認・修正画面
  ↓
利用者による確定後に保存
```

## 現時点のデータ量評価

- 場合別1：8分類、全7,682件に値があり、主要分類は評価可能。
- 場合別2：403件（5.2%）が欠損。主要分類は評価可能だが、10件未満の分類もある。
- 発生場所1：3分類、全7,682件に値があり、評価しやすい。
- 発生場所2：26分類。主要分類は十分だが、10件未満の分類がある。

7,682件は既存LLMを利用した抽出システムの試作と主要分類の評価には十分である。一方、少数分類の性能を個別に保証する件数ではない。少数分類は明示語がある場合のみ候補を出し、それ以外はnullまたは人手入力とする。

この件数は実運用性能を保証しない。既存値は暫定比較用ラベルとして使用し、最終評価では原文から判定可能かを人が独立に確認した正解データを用いる。

## 入力・表示の安全対策

- 入力長に上限を設け、入力文をプロンプト内で明確にデータとして区切る。
- 入力文中の「指示を無視せよ」等を命令として扱わない。
- LLMに外部ツール実行、ファイル操作、URLアクセス、DB更新権限を与えない。
- 確認画面へ原文や根拠を表示するときはHTMLをエスケープする。
- AI抽出値、規則による派生値、nullを画面上で区別する。
- 全項目を人が確認済みにするまで確定保存しない。
