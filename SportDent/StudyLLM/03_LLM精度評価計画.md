# LLM構造化抽出の精度評価計画

## 評価目的

自由記述からDB項目を自動入力したとき、「自動入力された値の誤りを極力少なくできるか」を評価する。網羅率より適合率を優先し、不明な場合はnullを許容する。

既存DB登録値は暫定比較用ラベル（silver label）とし、人が原文から判定した値を最終的な正解（gold standard）とする。

## データ分割

同じ事例を指示文の調整と最終評価の両方に使わない。

1. 開発用：指示文、同義語辞書、null基準の調整に使用
2. 検証用：自動入力を許可する閾値と規則の決定に使用
3. 最終評価用：開発完了後に1回だけ性能を算出

完全一致・近似重複・同一事例の可能性がある行は、必ず同じ分割に置く。分割方法、乱数seed、対象ID、除外理由を保存する。

既に全7,682件を見て作成した同義語候補や規則があるため、このデータ内から後で最終評価群を切り出しても完全な未使用評価とはいえない。後ろ向き評価では最新年度等の時間的ホールドアウトを優先し、最終的には新規利用者が入力した未使用文による前向き評価を行う。

推奨する評価構成は次のとおりとする。

1. 開発・内部検証：重複をグループ化した層別評価
2. 後ろ向き最終評価：開発中に内容を参照しない年度または事例群
3. 前向き評価：実際の入力画面で新たに作成された文章

具体的件数は、各項目で必要な非null出力数と信頼区間を試算してから固定する。単に100件という一律件数では決めない。

## 比較する値

LLMには事故状況の自由記述だけを渡し、既存DBの正解列を入力へ含めない。出力を次と比較する。

- 場合別1・2
- 発生場所1・2
- 競技種目
- 通学方法
- 遊具等

既存DB値にも誤記や入力規則の揺れがあり得るため、不一致事例だけを確認してはならない。LLMとDBの一致例、不一致例、LLMのnull例、DB欠損例から無作為に抽出し、人が確認する。

最終評価用の正解は、DB値とLLM値を伏せた状態で2名が独立判定し、不一致を第三者または合議で調停する。各項目について「原文から判定可能か」と「判定可能なら正しいDB値」を別々に記録する。

## 必須指標

| 指標 | 意味 |
|---|---|
| 適合率 | LLMが値を入れたうち正しかった割合 |
| 再現率 | 原文から判定できる項目のうちLLMが正しく入力できた割合 |
| カバー率 | 全対象のうち非nullを返した割合 |
| 誤入力率 | 全自動入力のうち誤っていた割合 |
| 安全棄権率 | 原文から判定不能な項目を正しくnullにした割合 |
| 過剰棄権率 | 原文から判定可能なのにnullにした割合 |
| 共同適合率 | 値と根拠文字列の両方が正しかった割合 |
| 全項目完全一致率 | 1事例の対象項目がすべて正しかった割合 |
| 人による修正率 | 確認画面で値またはnull理由が修正された割合 |
| Macro-F1 | 少数カテゴリを含めたカテゴリ間の性能 |
| Weighted-F1 | 実際の件数構成を考慮した全体性能 |
| Cohenのκ | 偶然の一致を考慮したDB値との一致度 |

「既存DBの欠損」「原文に記載なし」「曖昧」「非該当」「検証棄却」「処理エラー」は別の状態として集計する。nullを通常カテゴリとして一括してF1やκに混ぜず、値の分類性能と棄権性能を分けて報告する。

各主要指標には95%信頼区間を付ける。カテゴリ別件数が少ない場合は点推定だけで採用判断をしない。カバー率と誤入力率の関係は、selective risk–coverageとして併記する。

## 自動入力を許可する暫定基準

- 項目別の共同適合率について、片側95%信頼下限98%以上
- 検証前の上下位矛盾率を記録し、確認画面表示時の上下位矛盾0件
- 根拠文字列と原文位置の機械検証合格率100%
- 少数カテゴリはカテゴリ別評価ができる件数に達するまで「明記時のみ」または手入力
- 基準未達の項目・カテゴリは確認画面でnullとして表示

98%は暫定値である。実運用上許容できる誤入力数を決めたうえで最終決定する。例えば100件で誤り0件でも、98%以上を十分な精度で保証したとは限らない。項目ごとに必要な非null評価数を事前計算する。

## 段階的な導入

### 第1段階

主要かつ明記されやすい分類のみ自動入力する。

- 場合別1
- 登校中・下校中
- 体育・体育的部活動
- 発生場所1
- 道路、教室、体育館、運動場・校庭、廊下
- 明記された通学方法・競技種目

### 第2段階

検証データで基準を満たした詳細分類を追加する。

### 第3段階

少数分類を個別に評価し、十分な根拠があるものだけ追加する。

## エラー分析表に残す項目

- 匿名化した評価用ID
- 原文
- DB登録値
- LLM候補値
- 根拠文字列
- 最終判定
- エラー原因
- 修正规則の要否
- 人による修正時間
- status・棄権理由
- 抽出元（LLM明記・同義語候補・階層派生・人修正）
- モデル名・モデル版
- プロンプト版・辞書版・規則版
- 実行日時・応答時間・API失敗有無

## 主なエラー原因の分類

1. 原文に情報がないのに推測した。
2. 同義語を別カテゴリへ割り当てた。
3. 場合別1・2または発生場所1・2が矛盾した。
4. 複数の事故場面や場所から誤った対象を選んだ。
5. 否定表現や時系列を誤読した。
6. DBの登録値に疑義があった。
7. 原文だけではDB登録値を再現できなかった。
8. 原文中の命令・否定・引用を誤って採用した。
9. システム障害を判定不能として扱った。

## 比較する方式

LLMの追加価値と規則の効果を分けるため、同じ最終評価データで次を比較する。

1. 同義語・固定規則のみ
2. LLMのみ（構造化出力）
3. LLM＋許容値・根拠・依存規則

## 再現性の記録

- モデル提供者、モデル名、固定可能な版
- システムプロンプトと抽出プロンプトの版
- 温度等の生成設定
- 選択肢・同義語・依存規則の版
- 実行日、処理件数、費用、平均応答時間、失敗率
- 同じ入力を再実行した際の一致率

## 研究として報告する際の注意

本システムは入力支援であり、LLMが確定登録するものではないと明記する。精度だけでなく、自動入力できた割合、棄権理由別null率、人による修正率、入力時間短縮、処理失敗率も報告する。過去DB文による後ろ向き性能と、実際の利用者入力による前向き性能を区別する。
